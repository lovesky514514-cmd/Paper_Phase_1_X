## 2. 优点：它真的做对了什么

### 2.1 "估计状态"和"真实状态"被干净地分开了

`study.py:33-36`：

```python
observed    = [rng.uniform(0.94, 1.12) + 0.025 * t for t in range(3)]   # 策略看到的
deviation   = [rng.gauss(0, 0.06 if case_id % 5 else 0.16) for _ in range(3)]
hidden      = [max(0.3, a + b) for a, b in zip(observed, deviation)]     # oracle 看到的
hidden_derating = {"L01": 0.72} if case_id % 7 == 0 else {}
hidden_outage   = "L03"         if case_id % 11 == 0 else None
```

三个关键点：

1. **策略只能拿到 `observed`**（`checks.py:47-53` 的签名里只有 `observed_factor`）；
2. **oracle 只拿到 `hidden` + 隐藏的降额与断线**（`study.py:54-55`）；
3. **降额和断线对所有策略都不可见** —— 这是一个刻意设计的"信息盲区"，也是 23 个错误放行的主要来源。

这个设计比"让两个策略看不同数据"要严谨得多：它模拟的是**量测误差 + 未上报的工况变化**，正是立项书 §1 说的"混淆网架、单位、工况"。

### 2.2 独立 oracle 用了**不同的数值方法**，比同类项目更接近"独立"

| | `physics.solve_ac` | `oracle.evaluate` |
|---|---|---|
| 求解器 | `scipy.optimize.root`（hybr / 极坐标 V∠θ） | `scipy.optimize.limits` → `least_squares`（直角坐标 Re/Im） |
| 未知量 | 1 个参考角 + n-1 角 + n-1 幅值 | 2(n-1) 个直角分量，V₀ 固定 1.02 |
| 支路潮流 | `max(|S_from|, |S_to|)` | 同样双向取最大 |
| 收敛判据 | 残差 < 1e-7 | 残差 < 1e-6 |

`oracle.py:3-5` 的注释很准确：

> It uses a separately coded voltage residual and SciPy least_squares, but **shares the simplified AC equations: NOT an independent utility-grade solver.**

**它没有把"另一种写法"吹成"另一个求解器"**，这个分寸感比很多论文都好。（对照：02X 的 oracle 与验证器用了同一个函数同一个容差，见 `02dst.md` §3.1。）

### 2.3 split-conformal 分位数实现是教科书级的

`calibration.py:18-31`：

```python
values = sorted(past_absolute_errors)
rank = ceil((len(values) + 1) * (1 - alpha))
if rank > len(values):
    raise ValueError("insufficient calibration observations for chosen alpha")
return ErrorBand(values[rank - 1], len(values), alpha)
```

- 用的是**有限样本修正的秩** `⌈(n+1)(1-α)⌉`，不是简单的 `⌈n(1-α)⌉`——这是 conformal prediction 的正确写法；
- **样本不足时直接抛错**（fail closed），而不是悄悄缩小带宽；
- 校准序列来自**独立的随机流**（`study.py:25` 的 `seed + 100000`），且用了**与测试不同的 σ**（历史 0.045 vs 测试 0.06/0.16）——这是**故意的分布失配**，用来测覆盖率会不会塌。

绝大多数原型会"用测试集残差分位数当带宽"，那样覆盖率必然是 1。这里没有。

### 2.4 网关的 TOCTOU 防护是**双重检查**，而且是同一把事务锁内

`gateway.py:88-133` 的流程值得逐行看：

```python
with closing(self._db()) as db:
    replay = existing(db)                       # ① 事务外先查一次幂等
    if replay is not None: return replay
    snapshot = State(*db.execute("SELECT ...").fetchone(), ...)
...
decision = decide(...)                          # ② 在锁外做昂贵的 AC 计算
...
with closing(self._db()) as db:
    db.execute("BEGIN IMMEDIATE")
    replay = existing(db)                       # ③ 锁内再查一次幂等
    if replay is not None: db.rollback(); return replay
    current = State(*db.execute(...).fetchone())
    if current.version != snapshot.version:     # ④ 锁内重验版本
        db.rollback(); return {"verdict":"BLOCK","reason":"state changed during verification"}
    if proposal.expires_at <= time.time():      # ⑤ 锁内重验过期
        db.rollback(); return {"verdict":"BLOCK","reason":"request expired before commit"}
```

**"在锁外算 AC、在锁内再验一遍"** 正是立项书 §3 要求的"检查—执行之间状态一致性"的正确实现。而且：

- 幂等指纹是 `{proposal, policy}` 的哈希，**不含传感器快照**（`gateway.py:75-77` 注释点明"identifies the logical request, not a mutable sensor snapshot"）；
- `b1_direct`（无验证直放）被**明确禁止**走执行路径（`:57-58`）；
- 版本号只在 `ALLOW` 时递增（`:127-129`）；
- 响应里带 `n1_coverage: {checked, total}`（`:124-126`）——**主动暴露"N-1 只查了 2 条线"**，而不是宣称"全部 N-1 安全"。

## 3. 缺点：问题在哪

### 3.1 最致命：B2 / B3 / B4 的**每一个数字都相同**

`results/pilot.json`（seed=19，144 候选）：

| 策略 | oracle 不安全 | 错误放行 | 放行 | 弃权 | 3 步安全完成 | 平均预算单位 | 平均 AC 调用 | 平均 N-1 覆盖 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| B0 stop | 23 | 0 | 0 | 142 | 0 | 0.0 | 0.0 | 0.0 |
| B1 direct | 23 | **23** | 144 | 0 | 39 | 0.0 | 0.0 | 0.0 |
| **B2 DC** | 23 | **23** | **144** | 0 | **39** | 1.0 | 0.0 | 0.0 |
| **B3 AC** | 23 | **23** | **144** | 0 | **39** | 3.0 | 1.0 | 0.0 |
| **B4 两步 AC** | 23 | **23** | **144** | 0 | **39** | 6.0 | 2.0 | 0.0 |
| B5 UQ/N-1 | 23 | **0** | **7** | 0 | **0** | 15.5 | 4.6 | 1.59 |

**B2 = B3 = B4，一位不差。** 这意味着：

> **用 DC 单步、用完整 AC 单步、用两步 AC 滚动——在本实验里没有任何区别，一次错误放行都没多拦住。**

原因在数据生成时就定了：错误放行的根源是 `hidden = observed + deviation`，也就是**状态估计错了**。在错误的状态上算 DC 还是算 AC，**都会得出"安全"的结论**。模型保真度（DC→AC）**完全无法弥补量测误差**。

这是对立项书的一个**决定性**检验结果，而且是对作者有利的那一半：

- ✅ 支持了立项书的核心论点"单步验证不够、必须处理不确定性"；
- ❌ 但同时说明**立项书 §4 的"创新点 II（多步依赖与 N-1 联合约束）"在本设置下贡献为 0**；
- ❌ 也说明"分层验证预算"（RQ3 / 创新点 III）**没有检验空间**：B4 只花 6 个单位，预算 45 根本用不完。

**这不是"调参没调好"，是"这个实验根本无法区分 AC 与 DC"。** 如果论文里保留"分层 AC/N-1"的主线，必须先造出一个只有 AC 能发现、DC 发现不了的案例（例如电压越限、网损导致的分布差异），否则这条主张必须删掉或降为"支撑性工程贡献"。

### 3.2 第二个致命：B5 用 **94.2% 的安全动作拒单率** 换来 0 错误放行

把上表换算成"保护质量"：

```text
144 个候选 = 121 个真实安全 + 23 个真实不安全
B5 放行 7 个（全是安全），拒绝 137 个
  → 拦住的真不安全：23 / 23 = 100%
  → 误杀的真安全：114 / 121 = 94.2%
```

`completed_safe_tasks = 0`，即**没有任何一个三步任务能完整走完**。

为什么会这样？看 `checks.py:92-121` 的 B5 路径：

```python
factors = band.factors(forecast_factor)      # 返回两个端点 (下界, 上界)
for factor in factors:
    dc  = solve_dc(...)  ; 检查
    ac  = solve_ac(...)  ; 检查
    for outage in ("L01","L02"):
        fault = solve_ac(..., outage=outage); 检查
```

- `factors` 是 `(observed - 0.0686, observed + 0.0686)`；
- **上界端点 = observed + 0.0686**，而 observed 分布在 0.94–1.17，所以上界最高到 1.24；
- toy5 的线路额定是紧的，**1.24 的负荷因子几乎必然热越限** → BLOCK。

于是 B5 实际上在做：**"假设负荷比测量值高 7%，如果那样会越限就拒绝"**。在真实负荷因子根本没到那个水平时，它把 94% 的正常动作杀掉了。

立项书 §4 写的正是这个：

```text
max_{u∈U_t} g_i(F( x̂_t, a_t, u )) ≤ 0,  ∀i ∈ H
```

**这是"最坏情况必须可行"的鲁棒硬约束，不是"以 90% 概率可行"的机会约束。** 所以 94% 的拒单率是**这个数学形式的必然结果**，而不是实现 bug。

而立项书 §4.3 里同时写了另一套东西：

```text
J = E[C_op] + λ1·CVaR_α(L_soft) + λ2·C_verify + λ3·C_delay
```

**CVaR 在代码里完全不存在。** 也就是说：立项书写了"硬约束版"和"软目标版"两种形式，实现只做了硬约束版，而硬约束版恰好不可用。**改法很明确：把 `C_t + r_t(a) ≤ B` 这类硬边界改成 CVaR 约束（例如"越限概率 ≤ 10%"），然后重跑。**

### 3.3 校准确实塌了，而且数据支持这个结论

| seed | 名义覆盖 | 实测覆盖 | B5 放行 | 错误放行 | 完成 |
|---:|---:|---:|---:|---:|---:|
| 19 | 0.90 | **0.6597** | 7 | 0 | 0 |
| 29 | 0.90 | **0.7500** | 6 | 0 | 0 |
| 39 | 0.90 | **0.7431** | 10 | 0 | 1 |

带宽 `size = 0.06855`，而测试误差是 `N(0, 0.06)`（80% 案例）+ `N(0, 0.16)`（20% 案例）。**故意的分布失配**让覆盖率只有 0.66–0.75。

这是本项目最有价值的实证发现之一：**conformal 的交换性假设一旦破了，覆盖率会以很直接的方式塌掉，而"0 错误放行"这个漂亮数字正是靠过度拒单掩盖了这层失效。** 这句话如果写进论文的 Threats to Validity，比任何正面结果都更有分量。

但它也暴露一个逻辑问题：既然带宽**偏窄**（覆盖率不足），按理 B5 应该**更容易放行**才对；实际却只放行 7 个。说明**拒单的主导因素不是"带宽多宽"，而是"检查的是上界端点本身"** ——再次指向 §3.2。

### 3.4 一半的昂贵预算花在"不可能失败"的方向上

`calibration.py:14-15`：

```python
def factors(self, observed_load_factor):
    return (max(0.1, observed_load_factor - self.size),
            observed_load_factor + self.size)
```

下界端点 = **更低的负荷**。而 toy5 的三类约束（线路热稳定、母线电压、机组出力）里，**负荷越低越安全**：线路潮流下降、电压升高但通常仍在区间、机组出力不变。所以下界端点**结构上几乎不可能触发 BLOCK**。

但代码对两个端点做**完全相同**的检查（DC 1 + AC 3 + 2×N-1 3 = 每端点 10 单位）。于是：

- 每个时间步烧 20 单位，其中**10 单位（50%）用于一个物理上不可能失败的方向**；
- 三步 × 两步 = 平均 15.5 单位（因为有提前 BLOCK 退出），仍然浪费近半。

**这是最容易修、收益最直接的一条**：只保留上界端点，或对每条约束分别判定"最坏方向"（热稳定取上界、电压下限取下界），预算直接省一半。

### 3.5 toy5 太小，导致"安全/不安全"的判据空间很窄

`model.py` 里的 toy5 是 5 母线、4–5 条线，`config.contingencies = ("L01", "L02")`，而**隐藏断线一直是 L03**（`study.py:37`）。所以：

- 检查器永远不检查真正会断的那条线；
- `n1_coverage` 报告 "checked 1.59 / total 5" → 覆盖率约 32%，**从一开始就不可能覆盖 L03**；
- 隐藏降额是 `L01 → 0.72`（第 7 个案例一次），这项**任何策略都不知道**。

**结论：23 个"不安全"里，有相当一部分是"信息上不可检出"的**（断 L03、降额 L01），任何方法都拦不住。这让 FAR 的分母里混进了不可解项，B1–B4 的 23 次错误放行因此不能全部算作"验证失败"。

**改进**：把"可检出"与"不可检出"的不安全案例分开统计（这正是立项书 §5.4 要求的"记录未覆盖部分"），否则审稿人会问"你的方法怎么可能拦住它不知道的事"。

## 4. 项目自己已经承认的负结果与红线

1. **"安全门可能过度保守导致三步任务完成率近零"**（`QUALITY.md:9`）。

## 7. 在全系列里的定位建议

| 关系 | 说明 |
|---|---|
| 与 01X（可靠性） | 01X 的 `task_budget` 常数与本文的 `band.size` 是同一类问题：**一个常数决定了整个结论**。两篇都应该做参数扫描 |
| 与 02X（科学仿真） | 02X 的 oracle 与验证器同源；本文的 oracle 换了求解器与坐标，**独立性做得更好**。02X 应该参考本文的写法 |
| 与 04X（因果） | 本文的"隐藏断线/降额"就是 04X 说的"隐藏混杂"；两篇可以共享"信息盲区"的表述 |
| 与 05X（安全博弈） | 本文的"硬约束 + 软优化"分层，与 05X 的"硬授权永不让步 + 软资源分配"几乎是同一个架构；05X 写得更清楚，本文实现得更完整 |

**推荐定位**：**五份里"最该把负结果写出来"的一份。** 理由：

- 它已经有两块别人很难快速复制的资产：**独立的 AC oracle** 与 **TOCTOU 安全的幂等网关**；
- 它的负结果（AC 无差别、UQ 门控不可用、覆盖率塌陷）**每一条都能独立成文**，而且比"我们又提升了 3%"更有价值；
- 但它的正面结论目前是 0（`completed_safe_tasks = 0`），所以在 P0-1/P0-2 完成前**不能写 Results 段落**。

**建议的两条路线**：

- **路线 A（保守，推荐先做）**：先做 P0-1 + P0-2 + P1-2，如果能把"错误放行 ≤2 且完成 ≥10"做出来，就沿着"不确定性校准的调度门控"投 EPSR / SEGAN。
- **路线 B（诚实，风险低）**：把现有三组种子 + 三个负结果写成一篇 **"为什么在估计状态上做 AC/N-1 检查救不了 Agent 调度"** 的经验/评测论文，投 SMPT 或 QREI 这类接受负结果与方法学的刊。立项书 §5 的 go/no-go 判据本来就写了要"诚实报告 Pareto 权衡"。
